`api.truelabel.fun` runs on a single droplet. nginx terminates TLS and
proxies to the backend binary on `127.0.0.1:8080`, which systemd keeps
running. No Kubernetes, no container orchestration, in production today.

```
firewall (22, 80, 443 only)
  → nginx (TLS, edge rate-limit caps)
    → 127.0.0.1:8080 (systemd: truelabel-backend.service)
```

Everything below lives in `deploy/` at the repo root.

## The two settings that matter

Everything else here is convenience. These two are not — get them wrong
and the rate limiter in [Rate Limiting](/docs/backend/rate-limiting)
silently stops working.

<Callout type="warn" title="SERVER_HOST=127.0.0.1, not 0.0.0.0">
  The default binds every interface, which leaves port 8080 answering the
  open internet beside nginx — without TLS, and without the header nginx
  adds. A caller reaching it directly writes `X-Forwarded-For` themselves
  and picks its own rate-limit bucket on every request, at which point the
  limits mean nothing. A firewall on 8080 is a good second belt, not a
  substitute — a container or VPN peer added later is already inside it.
</Callout>

<Callout type="warn" title="TRUSTED_PROXY_HOPS=1">
  Behind a proxy, every request arrives *from the proxy* — left at `0`,
  the peer address is `127.0.0.1` for everyone and the whole internet
  shares one rate-limit bucket. The global backstop is 3,000 requests/hour,
  so the API starts returning `429` to everybody within minutes of real
  traffic. Count only hops that append to the header: nginx alone is `1`,
  a CDN in front of it makes `2`. **Setting it higher than the truth is
  worse than leaving it at zero** — the surplus entries are the caller's
  own to forge.
</Callout>

The service logs an error at boot if it detects either mistake.

## Deploying

```bash
# Build for the droplet (Debian/Ubuntu, x86_64)
cargo build --release --target x86_64-unknown-linux-gnu
```

```bash
# On the droplet
sudo useradd --system --no-create-home --shell /usr/sbin/nologin truelabel
sudo install -m 0755 truelabel-backend /usr/local/bin/
sudo install -d -m 0750 -o root -g truelabel /etc/truelabel
sudo install -m 0640 -o root -g truelabel backend.env /etc/truelabel/backend.env
sudo install -m 0644 truelabel-backend.service /etc/systemd/system/

sudo cp nginx-api.truelabel.fun.conf /etc/nginx/sites-available/api.truelabel.fun
sudo ln -s /etc/nginx/sites-available/api.truelabel.fun /etc/nginx/sites-enabled/
# add the two limit_req_zone/limit_conn_zone lines to the http{} block first, then:
sudo nginx -t && sudo systemctl reload nginx

sudo systemctl daemon-reload
sudo systemctl enable --now truelabel-backend
```

Migrations run automatically at boot, so the database role needs `CREATE`
rights and must be able to `CREATE EXTENSION pg_trgm` the first time.

`truelabel-backend.service` is heavily hardened: `ProtectSystem=strict`,
an emptied capability-bounding-set, syscall filtering. `nginx-*.conf`
deliberately does **not** duplicate security headers — the app already
sets them on every response (see [Rate Limiting](/docs/backend/rate-limiting)
and [Authentication](/docs/backend/authentication)) — but does add
`limit_req`/`limit_conn` zones as a first line of defense that costs
nothing and never reaches the app.

## Checking it worked

```bash
# Loopback only: the first answers, the second must time out.
curl -s localhost:8080/health
curl -s --max-time 5 http://<droplet-ip>:8080/health

# Through nginx, with the headers the app sets.
curl -sI https://api.truelabel.fun/health | grep -Ei 'cache-control|strict-transport|x-frame'

# Real client addresses are reaching the app.
journalctl -u truelabel-backend -f | grep -i 'rate limit'
```

If a rate-limit warning ever names `127.0.0.1` as the subject, the hop
count is wrong and every user is sharing one bucket.

## Postgres and Redis

Both listen on loopback only — `listen_addresses = 'localhost'` and
`bind 127.0.0.1`. They hold every profile and every device-token hash, and
neither speaks TLS in this setup, so nothing but the API should be able to
open a socket to them.

## `k8s/` and `infra/` — not the current deployment

The repo also has Kubernetes manifests (`k8s/`, Kustomize base + overlays)
and Terraform for AWS/DigitalOcean (`infra/`), plus a GitHub Actions
workflow (`.github/workflows/ci-cd.yml`) that builds, pushes, and deploys
Docker images to an EKS cluster on push to `main`.

<Callout type="warn" title="This does not match production">
  That workflow targets an EKS cluster; the droplet above is what's
  actually live at `api.truelabel.fun`. Treat `k8s/`/`infra/` as
  experimental multi-cloud scaffolding, not the deployment path currently
  in use — and don't assume the CI workflow's deploy step reflects reality
  until it's updated to target the droplet (or the droplet is retired in
  favor of the cluster). If you're picking this up, that inconsistency is
  the first thing worth resolving one way or the other.
</Callout>
